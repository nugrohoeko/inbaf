# Final security and production configuration audit

Audit dates: 24–25 October 2026; report updated 25 October 2026. Runtime versions below were observed during this audit and were not upgraded. This report distinguishes application checks on the local workstation from checks that require the intended production infrastructure. No production deployment, environment change, data reset, runtime upgrade, or removal of existing data was performed.

**Decision: NOT READY FOR DEPLOYMENT.** The current PHP runtime lacks a critical security update, the local MySQL release is beyond community maintenance, and production infrastructure, HTTPS, mail delivery, monitoring, and recovery operations have not been verified. Passing dependency scans does not resolve runtime or deployment findings.

## Findings and fixes

| ID | Severity | Finding and root cause | Fix | Retest evidence |
|---|---|---|---|---|
| FSEC-01 | Medium | Self-registration accepted passwords beyond bcrypt's 72-byte boundary, unlike the password-change/reset paths. Different suffixes could be silently ignored. | Registration applies the byte boundary; a shared `BcryptPassword` rule covers every password write path. | Registration boundary test rejects oversized ASCII and Unicode passwords; accepts exactly 72 bytes and verifies the stored hash. |
| FSEC-02 | Medium | A NUL byte inside an otherwise valid new password reached bcrypt and raised an exception instead of a form-validation response. | The shared rule rejects NUL bytes before hashing in registration, account/legacy password changes, reset/activation, and administrator account creation. | The regression checks HTTP 422 on all five write paths, unchanged existing hashes, preserved reset token, and no invalid new account. |
| FSEC-03 | High | The browser rich-text sanitizer used a scheme denylist that missed encoded/control-character executable URLs and allowed foreign HTML namespaces. Imported/authored option text reaches `v-html`, so server sanitization of the question prompt alone did not cover that input. Production CSP is additional protection, not a replacement for sanitization. | `resources/js/security/sanitize.js` allows supported HTML tags/attributes, checks parsed URL protocols, removes SVG/MathML, and restricts images to the application origin or raster data URLs. `store.js` re-exports this implementation. | `tests/Browser/final-security.spec.js` checks obfuscated JavaScript/VBScript links, foreign namespaces, event handlers, remote image tracking, and preservation of ordinary formatting/safe links. The final browser runner records execution separately. |
| FSEC-04 | Medium | Concurrent registration requests could all pass the email uniqueness validator. The database correctly prevented duplicates, but losing requests returned an unhandled unique-constraint error. | `AuthController` translates a confirmed competing email claim into HTTP 422 after the transaction rolls back. Unrelated constraint failures are rethrown. | Ten synchronized PHP processes on an isolated MySQL QA copy: before fix 1 created/9 server errors; after fix 1 created/9 validation errors. The final repeat again returned 1 HTTP-equivalent 201 and 9 validation 422 responses; both response-distribution and exactly-one-user/profile/audit checks PASS. A deterministic SQLite feature regression also covers the race. Latest evidence: `tmp/qa/final/operations/registration-concurrency-latest.json`. |

The registration concurrency runner calls the actual controller, validation, database transaction, session, and authentication code. It deliberately synchronizes requests after the uniqueness query to exercise the race. It excludes HTTP transport and must not be described as an HTTP load benchmark. Its manifest path and generated database name are guarded; it accepts only an existing isolated `inbaf_qa_rc_<12 hex digits>` database distinct from the configured database.

## Read-only production preflight

Run `php artisan inbaf:readiness --json` against the intended release environment. The command changes no configuration or data and omits configuration values and secrets. It validates 42 local configuration/artifact/runtime requirements and lists eight independent infrastructure/operational requirements as `NOT TESTED`.

The workstation run saved in `tmp/qa/final-readiness.json` reports **33 PASS, 9 FAIL, 8 NOT TESTED**, exit code 1; the final rerun confirmed the same counts. The failures are environment, debug mode, HTTPS base URL, production host, secure session cookies, mail transport, sender identity, PHP patch baseline, and development asset marker. These are observations of local configuration, not assertions about an unprovided production server.

The command intentionally cannot certify deployment readiness: mail delivery, database/migrations, workers/scheduler, TLS/document root, current advisory scans, backup/restore/rollback, monitoring and capacity require separate evidence. It returns `NOT READY FOR DEPLOYMENT` until those external checks are independently reviewed in the final release report. Use [deployment.md](deployment.md) for deployment/rollback procedures and Laravel's [production deployment guidance](https://laravel.com/framework/docs/deployment) for configuration-cache and debug requirements.
